# Generating Graphics — instructions for code-claude

You (code-claude) generate the game's graphics yourself: decide what's needed, write a
spec, run the generator, then wire the results into the game. This guide tells you exactly
how. Work from the **game project directory**; call the tool by its full path.

> **See also:** **ASSET_SOUND_SPEC_GUIDE.md** for audio, and
> **MESHY_SKILL_GUIDE.md** for 3D models — the default image-to-3D path uses a
> clean reference image generated by *this* tool (delivered to
> `core/assets/img/generated/`), so the two guides chain together.

## Concurrent runs are safe — they queue automatically

If another image run is already in progress (e.g. another code-claude requested art at the
same time), your run will **wait its turn** and print "another generation is running —
queuing". This is expected — let it wait; it proceeds when the other finishes. You don't
need to coordinate manually.

- Each run writes its own `delivery_<spec>_<timestamp>_<pid>.json` (plus a
  `delivery_latest.json` pointer), so parallel runs never overwrite each other's manifest.
  Read the delivery file your run prints at the end, not a fixed `delivery.json`.
- Rate-limit (429) errors are retried automatically with backoff — don't treat a transient
  rate-limit as a failure.
- Image runs and sound runs use separate queues, so generating art and audio at the same
  time is fine; only multiple *image* runs serialize against each other.

## The spending rule — ALWAYS dry-run and WAIT

**You must never spend API credits without explicit human approval.** The flow for every
batch is:

1. Write the spec JSON (into the game project, e.g. `art_specs/<name>.json`).
2. Run with `--dry-run` — this only prints the cost estimate and validates the spec; it
   generates nothing and costs nothing.
3. **Show the human the dry-run output (the per-item plan and total) and ASK for approval.**
4. Only after the human says yes, run the real command (same line, without `--dry-run`).
5. Read the run's `delivery_<spec>_<timestamp>_<pid>.json`, copy/move images into the
   game's asset folder, wire them in by id, then record provenance (see below).

Do not skip step 3. Do not run the non-dry-run command on your own initiative.

## The spec format

```json
{
  "project": "stone-age-civ",
  "defaults": {
    "model": "gpt-image-1.5",
    "size": "1024x1024",
    "quality": "medium",
    "background": "transparent",
    "style": "16-bit pixel art, top-down, cohesive earthy palette, clean readable silhouette"
  },
  "items": [
    { "id": "hut_thatch", "prompt": "a small thatched stone-age hut seen from above" },
    { "id": "spearman",   "prompt": "a stone-age spearman, side view, idle pose", "n": 3 },
    { "id": "title_bg",   "prompt": "sweeping stone-age valley at dawn",
      "model": "gpt-image-2", "size": "1536x1024", "background": "opaque", "quality": "high" }
  ]
}
```

## Fields

- `project` — short name, copied into the delivery manifest.
- `defaults` — applied to every item; each item can override any of them.
- `items` — each needs a unique `id` and a `prompt`.
- `id` — unique, becomes the filename (`spearman.png`). snake_case.
- `prompt` — what to draw. Be concrete about subject, view angle, pose.
- `model` — `gpt-image-1.5` (default; supports transparency) / `gpt-image-2`
  (best quality, **opaque only**) / `gpt-image-1-mini` (cheapest).
- `size` — `1024x1024`, `1024x1536` (portrait), or `1536x1024` (landscape).
- `quality` — `low` (drafts), `medium` (default), `high` (final/marketing).
- `background` — `transparent` (sprites/icons; needs a gpt-image-1.x model) or `opaque`.
- `output_format` — `png` (default, supports transparency) / `webp` / `jpeg`.
- `n` — variations to make (default 1). Filenames get `_v1`, `_v2`, …
- `style` *(defaults only, recommended)* — appended to every prompt for a cohesive look.

## Hard rules (the generator rejects violations)

1. **`background: "transparent"` requires a gpt-image-1.x model** (not gpt-image-2).
2. **`size` must be exactly** `1024x1024`, `1024x1536`, or `1536x1024`.
3. Every item needs a unique `id`.

## Guidance for good game art

- Sprites/units/icons/items → `gpt-image-1.5`, `transparent`, square, `medium`.
- Backgrounds/title/concept → `gpt-image-2`, `opaque`, landscape, `high`.
- For a consistent set, put the shared look in `defaults.style`; keep each `prompt` to just
  the subject + pose. Use `n: 3` to give options.
- Draft cheap: `quality: "low"` first pass, then re-render winners at `high` (each spend
  still needs approval).
- Always state the view angle (top-down / side / 3-quarter).
- Put "transparent background" in the prompt text too, to reinforce the parameter.

## Animation frames — use IMAGE-TO-IMAGE, not text-to-image (avoids frame drift)

When you need a second (or third) frame of an EXISTING sprite — a walk step, a
wing-flap, a slither, etc. — **do NOT generate it text-to-image from a fresh
prompt.** The model redraws the creature from scratch and the frame *drifts*: a
different art style, added/removed gear, shifted colors. Two independent
generations cannot be made to match, no matter how emphatic the prompt ("same
creature, only the legs move").

Instead, **edit the base sprite** (image-to-image) so only the pose changes and the
identity/colors/style are preserved:

```python
res = client.images.edit(
    model="gpt-image-1",
    image=open("assets/art/<id>.png", "rb"),   # the EXISTING base sprite
    prompt="Repose this exact creature mid-stride: one leg forward. Keep the "
           "IDENTICAL creature, colors, gear, art style and background — change "
           "ONLY the legs/pose.",
    size="1024x1024",
    background="transparent",   # else the edit fills the bg opaque black
    input_fidelity="high",      # KEY: preserves the input faithfully (incl. bg)
)
```

- `input_fidelity="high"` is the lever that keeps it on-model — without it the edit
  drifts and repaints the background. It also bills for the input image, so an edit
  costs ~2× a plain generation (the SDK can report `res.usage` token counts).
- The naming convention is `<base-id>_<frame>` (e.g. `goblin_anim1`,
  `player_..._walk1`); render code alternates base ↔ frame.
- Working reference: **`tools/img2img_anim.py`** (per-profile repose prompts for the
  124 monster frames, self-reports token cost). This is "low drift," not pixel-zero
  — for a hard zero-drift guarantee, animate the single sprite with code transforms
  (bob/sway/squash) instead of a second image.

## Rights, IP & provenance

- **Ownership (conservative):** under OpenAI's current terms, OpenAI assigns you its rights
  in the Output and **you are responsible** for the content. Whether a purely AI-generated
  image is *copyrightable* varies by jurisdiction. The generator writes a conservative
  `rights_note` into each manifest and points to the live terms
  (<https://openai.com/policies/terms-of-use>) — don't restate ownership more strongly than that.
- **Don't prompt for someone else's IP.** The generator scans prompts for a heuristic set of
  brands / franchises / characters / "in the style of <Name>" phrasing and, on a real run,
  **blocks** on a hit. If it's a false positive or the human confirms they hold the rights,
  re-run with `--allow-ip-risk` (recorded). It's a tripwire, not a clearance check — don't
  write prompts like "Mario" or "in the style of <living artist>".
- **Provenance is automatic.** Every PNG carries an embedded provenance chunk (id, prompt,
  model, timestamp, provider, terms URL, disclosure, pixel `sha256`, caller), mirrored to
  `get-graphic.log.jsonl`. Verify any asset with `get-graphic.py --verify <file-or-folder>`.
- **Identify yourself to the generator.** Always pass `--caller-id "<your code-claude id>"` (or
  set the `GETGRAPHIC_CALLER` env var) when you invoke it, so every log line and embedded chunk
  records which code-claude generated the asset. Add `--disclosure "..."` for how AI use is disclosed. **Kept safe automatically:** every generated image is also copied into the shared asset archive (`_asset_archive/graphics/`, content-addressed + a timestamped copy) so an original survives even if the game copy is edited or lost — `--no-archive` skips it, `--archive DIR` redirects.

## After generating

The run writes images to `--out` and a unique `delivery_<spec>_<timestamp>_<pid>.json`
(id, file, path, prompt) — the exact name is printed at the end of the run, and
`delivery_latest.json` always points to the most recent. Move the images into the game's
asset folder, then wire each into the game by its `id` (add the id to the `Assets.IDS`
allow-list — see the "Art assets" section in `docs/MODDING.md`).

## Never delete an asset — archive the old version (REQUIRED)

When you regenerate, replace, or retire an existing asset, **do not delete or
overwrite the old file**. Move the previous version into an `unused/` subfolder with
a timestamp suffix on the filename first:

```
assets/art/unused/<name>_<YYYYMMDD-HHMMSS>.png      # art
assets/sounds/unused/<name>_<YYYYMMDD-HHMMSS>.<ext> # audio
```

Generated assets cost credits and can't be reproduced byte-for-byte, so an archive
is reversible where a deletion is not. The `unused/` folder is a subfolder, and the
`assets` test scans `assets/art/` non-recursively, so archiving there never trips
the `Assets.IDS` ↔ files cross-check.

## Record provenance (REQUIRED — CI fails without it)

The per-run delivery files are gitignored (per-run, absolute paths), so the as-built prompts
must be folded into the committed `art_provenance.json`. After copying the PNGs in, run:

```bash
python tools/merge_delivery.py path/to/delivery_<spec>_<timestamp>_<pid>.json
```

This merges the run's records (id → prompt + params) into `art_provenance.json`
(committed, keyed by id, last-write-wins). The `assets` test FAILS if any delivered PNG
lacks a provenance entry, so this is not optional — do it before `node tests/run.js`.
`art_provenance.json` is the durable, diffable record that survives a clone (where the
binaries don't). Commit it alongside the `Assets.js` registration.

Finally, run `node tests/run.js` (expect `0 failed`) and report to the human what you
delivered and what (if anything) failed.
